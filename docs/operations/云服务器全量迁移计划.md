# 云服务器全量迁移计划

> 盘点日期：2026-07-31  
> 适用范围：旧服务器 `47.86.225.83` 上的全部业务项目、共享入口、运行状态、密钥文件、历史备份和必要运行缓存  
> 目标：迁移到椰子云 `156.225.23.248`，同时保持 `https://gw.hbcsch.pw` 和现有公网 URL 路径不变  
> 安全要求：本文不记录任何真实密钥、令牌、数据库连接串或完整签名 URL；密钥只通过 SSH 原样迁移

## 1. 先看结论

当前服务器不是单项目主机。它承载 4 个业务服务和 1 个共享 Caddy HTTPS 入口，必须作为同一次变更整体迁移：

| 业务 | systemd 服务 | 监听 | 主要目录 | 公网接入 |
|---|---|---:|---|---|
| 呈尚策划美工生图系统 PRO | `csgh-backend-gateway` | `0.0.0.0:8787` | `/opt/csgh-image-studio`、`/opt/csgh-gateway` | Caddy 默认路由 |
| 呈尚自动出餐系统 | `chengshang-auto-meal-worker` | `0.0.0.0:8797` | `/opt/chengshang-auto-meal` | 当前无 Caddy 路由，主要依赖进程内 worker |
| 双平台合同系统 API | `dpcs-api` | `127.0.0.1:8810` | `/opt/dual-platform-contract-system/dpcs-api` | Caddy 指定 `/api/...` 路由 |
| 门店资源 OCR | `dpcs-store-ocr` | `127.0.0.1:8800` | `/opt/dual-platform-contract-system/store-ocr-service` | Caddy `/store-ocr/*` 路由 |
| 共用 HTTPS、证书和更新分发入口 | `caddy` | `80/443` | `/etc/caddy`、`/var/lib/caddy` | `gw.hbcsch.pw` |

迁移采用以下方式：

1. 优先为旧系统盘创建阿里云整盘快照；如果椰子云无法提供目标机快照，则按第 6.2 节建立“旧机保留 + 新机全量归档 + 本地副本 + 抽样恢复”的替代恢复链，不能把新机本身当成唯一备份。
2. 新机是 Ubuntu 22.04，而旧机是 Alibaba Cloud Linux 3；保留新机网络、机器 ID、SSH 主机密钥和启动分区，业务运行时必须在 Ubuntu 上重新构建。
3. 先在线预复制，再在停写窗口执行保护目标机运行时的第二次增量同步，并基于最终源码重新构建和复核依赖。
4. 新机验收通过后，旧机 Caddy 临时把缓存未过期的流量转发到新机，避免新旧业务进程同时写入。
5. DNS A 记录切换到新 IP；旧机至少保留 7 天，不立即释放。

最重要的五条红线：

- 新旧两台服务器上的自动出餐 worker 绝对不能同时启用，否则可能重复执行任务。
- `/opt/csgh-image-studio` 有 130 项未提交内容，其他两个项目目录没有 Git 元数据，不能用重新 clone 代替目录复制。
- 旧网关二进制依赖 `libssl.so.1.1`，新机只有 `libssl.so.3`；不得通过安装过期兼容库强行运行，必须从迁移后的完整工作树重编译。
- 旧 Python venv 和 Node/Playwright 依赖来自另一发行版；目录需要归档保留，但正式运行环境必须在 Ubuntu 22.04 上重建并完成真实业务验证。
- 最终增量同步不得用未加排除项的 `rsync --delete` 覆盖新机已经重建的网关二进制、Rust `target`、`node_modules` 或 Python venv。

### 1.1 旧服务器保全与“替换连接信息”的边界

本计划执行的是复制迁移，不是把旧机文件移动走：

- 所有预复制和最终复制都由新机主动从旧机读取；正常迁移阶段没有任何删除旧机文件、卸载旧机软件或覆盖旧机系统的命令。
- 第一次预复制、目标机运行时重建和隔离验收期间，旧机 5 个生产服务保持原样运行；每轮复制后都必须按第 9.4 节复查旧机健康。
- 只有最终停写窗口才短暂停止旧机业务。切流后旧机磁盘、配置和项目仍完整保留，实例不释放；业务 unit 保持 disabled 是为了避免双写，可按第 16 节恢复为生产。
- 旧机和新机不能同时启用自动出餐 worker。“旧机仍可正常运行”是指切换前持续生产、切换后完整可回滚，不是两台机器永久同时处理同一批任务。

完整执行本手册并通过验收后，各项目的运行路径和公网 URL 均保持不变。只使用 SSH 做部署或运维的项目，确实只需把连接目标从旧机改为新机；业务客户端继续使用原域名，不需要改成裸 IP：

| 连接项 | 旧值 | 新值 | 是否改代码 |
|---|---|---|---|
| SSH/部署目标 | `admin@47.86.225.83:22` | `admin@156.225.23.248:22` | 只改部署配置 |
| 公网业务根地址 | `https://gw.hbcsch.pw` | 保持不变 | 否 |
| 服务器项目根目录 | `/opt/...` | 保持不变 | 否 |
| 同机服务地址 | `127.0.0.1:8787/8797/8800/8810` | 保持不变 | 否 |
| 密钥文件路径 | 现有 `/opt/...` 路径 | 保持不变 | 否 |
| 第三方看到的出口 IP | `47.86.225.83` | `156.225.23.248` | 改白名单，不改业务代码 |

本机已把两台服务器的非密码 SSH 配置保存在 Git 忽略的 `.env.ssh.local`。当前初始化阶段新机公钥目标是 `root`；完成第 7.3、7.4 节后，所有项目和自动化必须统一使用 `admin`。不能把“替换 SSH 主机”理解为可以跳过 Ubuntu 运行时重建、外部白名单、最终增量、DNS 切换和单 worker 门禁。

`.env.ssh.local` 只保存私钥路径，不复制私钥本身。为防 Windows 重装或磁盘损坏导致失联，应把私钥放入公司批准的加密备份，或在新机 `admin` 下登记第二把受控运维公钥；禁止把私钥提交仓库或上传普通网盘。

## 4. 目标机要求和禁止切换条件

### 4.1 推荐规格

- 4 vCPU、8 GB RAM 或更高。
- 80 GB SSD 或更高。40 GB 已有 65% 使用率，不足以同时保留增长空间和旧机归档。
- x86_64 架构，避免现有 Rust 二进制、Python wheels、PaddlePaddle 和 Chromium 不兼容。
- 同发行版迁移风险最低；本次目标已确定为 Ubuntu 22.04，因此必须执行本文的跨发行版重建流程，不能直接复用旧 venv 和网关二进制。
- 香港或网络质量相当的地域，并确保可稳定访问 Supabase、MongoDB、OSS 和所有 image-2/OCR 上游。
- 固定公网 IP 或可长期绑定的 EIP。

本次新机的 8 vCPU、8 GB 级内存和 100 GB 总盘容量达标，但 70 GB 数据盘当前未挂载，30 GB 系统盘单独使用不达标。第 7.2 节存储布局完成并通过重启验证后，才视为容量门禁通过。

### 4.2 网络和安全

服务商安全组与 Ubuntu UFW：

- 22/TCP：仅允许运维来源 IP。
- 80/TCP：允许公网，用于 HTTPS 跳转和 ACME。
- 443/TCP：允许公网。
- 8787、8797、8800、8810：不得在安全组或 UFW 对公网放行。
- 出站：允许访问 HTTPS、DNS，以及 MongoDB 实际使用的远端端口。

椰子云控制台当前没有已绑定的安全组，新机 UFW 也未启用。两层至少有一层必须明确执行默认拒绝入站，推荐两层都配置。不要把“业务尚未监听端口”误认为防火墙已经生效。

迁移工作站关闭 VPN 后可直接连接新机；开启原 VPN 时，连接在 SSH banner 前被服务商网络关闭。正式迁移必须固定使用已验证的非 VPN 出口，或从旧服务器 `47.86.225.83` 作为跳板连接，并在工单中记录实际来源 IP。

不要从旧机复制并覆盖这些活动文件：

- `/etc/machine-id`
- `/var/lib/dbus/machine-id`
- `/etc/ssh/ssh_host_*`
- `/etc/fstab`
- `/etc/sysconfig/network-scripts/` 或其他网卡配置
- cloud-init 实例状态、引导加载器和分区表

旧文件可以放进 root-only 归档，但新机必须保留自己的机器身份、磁盘 UUID、网络配置和 SSH 主机密钥。

### 4.3 No-Go 门禁

以下任一项未完成，不得切换：

- 旧机没有可独立恢复的来源：优先是阿里云系统盘快照；若快照不可用，必须有完整本地归档存放在新机之外，并完成抽样恢复验证。
- 椰子云目标机没有可验证的云快照时，未完成“旧机原样保留、新机全量归档、本地副本、校验清单和恢复演练”替代方案。新机本地归档不能作为唯一恢复源。
- 新机 `/dev/vdb1` 尚未持久挂载到 `/srv`，或 `/opt` 尚未 bind 到 `/srv/opt` 并通过重启验证。
- 完整归档、wheelhouse 和目标机运行时重建后，`/srv` 可用空间不足 15 GiB。
- 新机仍为 UTC、NTP 未同步，或系统更新后尚未重启。
- 新机无法通过 `admin` 公钥登录和 sudo。
- 新机初始 root 密码尚未轮换、仍允许远程 root/密码登录，或服务商安全组/UFW 尚未完成 22、80、443 最小放行。
- 新出口 IP 尚未加入 MongoDB、OSS、Supabase 网络限制和第三方 API 白名单。
- 自动出餐项目尚未确认 8797 的消费者和单 worker 方案。
- Ubuntu 上重新构建的 Rust 网关、Node 依赖、Python 3.11 venv、Playwright 和 PaddleOCR 尚未通过兼容性验证。
- 新机 Caddy 无法通过 `curl --resolve` 完成 HTTPS 测试。
- 任一本机健康检查失败，或 Caddy 三条公网路由失败。
- Playwright Chromium、PaddleOCR 模型或 Python venv 仍有缺失动态库。
- 未完成一次真实生图、合同查询和 OCR 冒烟测试。
- 回滚执行人、DNS 权限或旧机 Caddy 原配置备份缺失。

### 6.2 快照和恢复演练

椰子云已确认不提供实例云备份，只能由用户自行备份到本地。因此不能通过椰子云控制台一键回滚；迁移回滚依靠旧机和 D 盘本地明文归档完成。迁移仍然可以进行，但必须接受“重装新机后重新复制和重建”的恢复方式。

#### 6.2.1 优先方案：旧机系统盘快照

1. 在阿里云控制台对旧机系统盘创建手工快照，名称包含迁移日期和 `MIGRATION_ID`。
2. 等待快照状态变为成功，记录快照 ID、完成时间和磁盘 ID。
3. 最好用该快照临时创建一台不接公网业务的恢复实例，确认文件系统可挂载且 `/opt`、`/etc/caddy` 和四个密钥文件存在。
4. 快照完成前不要清理旧日志、备份或构建缓存。

#### 6.2.2 椰子云无快照时的替代恢复链

以下四项必须全部完成，才能进入正式复制和切流：

1. **旧机保留**：旧服务器 `47.86.225.83` 不关机、不释放、不删除文件。预复制、目标机重建和切流观察期内，旧机是第一回滚源；旧机服务只在最终停写窗口按本文顺序短暂停止。
2. **新机全量归档**：按第 9.2 节把旧机的 `/rootfs`、`/root-home`、`/home`、`/opt`、`/boot-efi` 和必要的活动缓存复制到新机 70 GB 数据盘的 `/srv/legacy-server`，保持 root-only 权限，并生成文件清单和 SHA-256 校验记录。
3. **新机之外的本地副本**：把完整持久文件归档和校验文件保存到迁移工作站的 `D:` 盘。本次按用户要求不启用 BitLocker 或其他加密，归档中的 `gateway.env`、Cookie、SSH 私钥和数据库连接串会以明文存在；因此备份目录必须限制为当前 Windows 用户、SYSTEM 和本机管理员可访问，不能上传普通网盘、公开 OSS 或提交仓库。具体 Windows 备份步骤见第 6.2.3 节。副本完成后必须直接校验并抽样恢复 `/opt`、`/etc/caddy`、服务 unit 和四个密钥文件。
4. **恢复演练**：在新机上使用归档做一次不接公网的临时恢复演练，至少验证目录结构、文件数量、关键文件权限、Caddy 配置、systemd unit、网关状态目录和合同/OCR/自动出餐状态目录。演练失败时停止迁移，不得用“文件已经复制”代替可恢复性证明。

本方案保证旧机仍可完整回滚，也能在椰子云重装新机后重新复制并重建运行环境；它不等同于云厂商快照，无法提供秒级整机恢复。旧机快照或本地副本至少要有一个位于新机之外，才能满足“旧服务器所有内容不会因新机故障丢失”的要求。由于本次本地副本不加密，备份盘丢失或被他人读取会暴露服务器敏感信息；这是明文备份的已知风险。应用级归档负责保全数据，Ubuntu 上重新构建负责让新机正常运行，二者不能互相替代。

#### 6.2.3 备份到本地 Windows 工作站

椰子云确认不提供云备份后，本节是正式迁移前的强制步骤。“本地备份”指迁移工作站的 `D:` 盘，不是新服务器的 `/srv/legacy-server`，也不是当前项目仓库目录。本次按用户要求直接保存明文，不启用 BitLocker；备份目录必须使用 NTFS ACL 限制访问。备份盘至少预留 40 GiB 可用空间，不得覆盖已有数据。

本地归档必须包含：旧机持久根文件系统、`/boot/efi`（如果存在）、`/etc/caddy`、全部 `/opt`、`/home`、`/root`、`/var`、`/usr/local`、`/srv`、服务 unit、密钥文件、Cookie/浏览器状态、活动状态目录、文件清单和 SHA-256 校验文件。Supabase、MongoDB、OSS 等外部系统的数据不在服务器文件归档内，仍按第 6.3 节分别确认其共享数据和白名单。

为避免旧服务器 40 GiB 根盘因临时压缩文件不足，不在旧机上生成完整压缩包，而是通过 SSH 将 `tar.gz` 流直接写入本地备份盘。旧机实测没有 `zstd`，因此这里使用远程 `gzip`。建议在 Windows 的 WSL 或 Git Bash 中执行下面的 Bash 命令；不要用 PowerShell `Out-File` 接收二进制归档流：

```bash
LOCAL_BACKUP_DIR='/mnt/d/secure-backups/csgh-server/2026-07-31'
OLD_IP='47.86.225.83'
OLD_USER='admin'
MIGRATION_KEY='/mnt/c/secure/migration_ed25519'

mkdir -p "$LOCAL_BACKUP_DIR"
test -d "$LOCAL_BACKUP_DIR"
df -Pk "$LOCAL_BACKUP_DIR"

ssh -T -o BatchMode=yes -o StrictHostKeyChecking=yes \
  -i "$MIGRATION_KEY" "${OLD_USER}@${OLD_IP}" \
  'set -o pipefail; sudo -n tar --acls --xattrs --numeric-owner --one-file-system \
    --exclude=./proc --exclude=./sys --exclude=./dev --exclude=./run \
    --exclude=./tmp --exclude=./mnt --exclude=./media --exclude=./lost+found \
    --exclude=./boot/efi --exclude=./srv/legacy-server \
    -C / -cf - . | gzip -1' \
  > "$LOCAL_BACKUP_DIR/rootfs-persistent.tar.gz"

ssh -T -o BatchMode=yes -o StrictHostKeyChecking=yes \
  -i "$MIGRATION_KEY" "${OLD_USER}@${OLD_IP}" \
  'set -o pipefail; if sudo -n test -d /boot/efi; then \
     sudo -n tar --acls --xattrs --numeric-owner -C / -cf - boot/efi; \
   else \
     sudo -n tar --acls --xattrs --numeric-owner --files-from=/dev/null; \
   fi | gzip -1' \
  > "$LOCAL_BACKUP_DIR/boot-efi.tar.gz"

test -s "$LOCAL_BACKUP_DIR/rootfs-persistent.tar.gz"
test -s "$LOCAL_BACKUP_DIR/boot-efi.tar.gz"
gzip -t "$LOCAL_BACKUP_DIR/rootfs-persistent.tar.gz"
gzip -t "$LOCAL_BACKUP_DIR/boot-efi.tar.gz"
sha256sum "$LOCAL_BACKUP_DIR"/*.tar.gz \
  > "$LOCAL_BACKUP_DIR/SHA256SUMS.txt"
```

如果旧机没有 `/boot/efi`，第二个归档仍应生成一个可验证的空归档；如果命令失败或生成文件为 0 字节，立即停止，不要删除旧机任何内容。归档完成后再生成不含文件内容的资产清单：

```bash
ssh -T -o BatchMode=yes -o StrictHostKeyChecking=yes \
  -i "$MIGRATION_KEY" "${OLD_USER}@${OLD_IP}" \
  'sudo -n bash -c '\''find /etc /root /home /opt /var /usr/local /boot /srv \
    -xdev -printf "%m %u %g %s %p\\n" 2>/dev/null | sort'\'' ' \
  > "$LOCAL_BACKUP_DIR/file-inventory.txt"
sha256sum "$LOCAL_BACKUP_DIR/file-inventory.txt" \
  >> "$LOCAL_BACKUP_DIR/SHA256SUMS.txt"
```

本次不使用 BitLocker、7-Zip 或其他加密。归档会明文保存服务器密钥、Cookie 和配置，只允许当前 Windows 用户、SYSTEM 和本机管理员访问；不要把备份目录加入 Git、云盘同步或公开共享。归档完成后执行以下完整性和内容抽样检查：

```bash

tar -tzf "$LOCAL_BACKUP_DIR/rootfs-persistent.tar.gz" \
  | grep -E '(^|/)(opt/csgh-gateway/secrets/gateway.env|etc/caddy/Caddyfile|opt/dual-platform-contract-system|opt/chengshang-auto-meal)' \
  | head -n 20
tar -tzf "$LOCAL_BACKUP_DIR/boot-efi.tar.gz" | head
```

本地归档至少做两轮：第一轮在旧机继续生产时作为基线；第二轮在最终停写、旧机服务按第 12 节停止后重新执行并写入新的带时间戳目录。两轮归档都保留，只有第二轮通过清单、校验和抽样解包后才能开始最终切流。旧机在观察期内不得删除，直到本地备份可读取且新机真实业务验收完成。

## 16. 回滚方案

### 16.1 DNS 切换前失败

这是最简单的回滚：

1. 停止新机全部服务，特别是自动出餐 worker。
2. 旧机恢复原 Caddyfile。
3. enable 并启动旧机生图、合同、OCR、Caddy。
4. 最后 enable 并启动旧机自动出餐 worker。
5. 验证现有 DNS 仍指向旧 IP 和全部现网功能。

旧机执行：

```bash
sudo cp -a "/etc/caddy/Caddyfile.pre-migration-${MIGRATION_ID}" \
  /etc/caddy/Caddyfile
sudo /usr/local/bin/caddy validate --config /etc/caddy/Caddyfile
sudo systemctl enable --now \
  csgh-backend-gateway dpcs-api dpcs-store-ocr caddy
sudo systemctl enable --now chengshang-auto-meal-worker
```

### 16.2 DNS 切换后失败

必须避免两台 worker 同时运行：

1. 立即 `disable --now` 新机自动出餐 worker。
2. 停止新机 Caddy 和其他业务服务，阻断继续写入。
3. 将新机有变化的本地状态反向同步回旧机，至少包括：
   - `/opt/csgh-gateway/state/`
   - `/opt/chengshang-contract-auth/storage-states/`
   - `/opt/dual-platform-contract-system/cookies/`
4. 旧机恢复 `Caddyfile.pre-migration-*`，验证配置。
5. enable 并启动旧机生图、合同、OCR、Caddy，真实验收通过后再 enable 并启动旧 worker。
6. 把 DNS A 记录改回 `47.86.225.83`；若走 GA，则把旧 IP 恢复为健康后端。
7. 为仍缓存新 IP 的客户端，在新机 Caddy 临时建立“新机转发到旧机”的反向桥，方式与第 13.2 节相同，只交换上下游 IP。
8. 保留该桥至少 `2 × TTL`，确认无流量后停止。

在新机的业务服务全部停止后，可用现有迁移密钥把少量可变状态推回旧机：

```bash
sudo rsync -aHAX --numeric-ids \
  -e "ssh -i ${MIGRATION_KEY}" --rsync-path='sudo -n rsync' \
  /opt/csgh-gateway/state/ \
  "admin@${OLD_IP}:/opt/csgh-gateway/state/"
sudo rsync -aHAX --numeric-ids \
  -e "ssh -i ${MIGRATION_KEY}" --rsync-path='sudo -n rsync' \
  /opt/chengshang-contract-auth/storage-states/ \
  "admin@${OLD_IP}:/opt/chengshang-contract-auth/storage-states/"
sudo rsync -aHAX --numeric-ids \
  -e "ssh -i ${MIGRATION_KEY}" --rsync-path='sudo -n rsync' \
  /opt/dual-platform-contract-system/cookies/ \
  "admin@${OLD_IP}:/opt/dual-platform-contract-system/cookies/"
```

状态回传后，在旧机恢复原 Caddyfile，并按 16.1 的顺序 enable/start 服务，自动出餐仍然最后启动。

回滚只恢复运行入口和本机状态。迁移期间已写入外部 MongoDB、Supabase 或 OSS 的业务数据不应删除；这些外部系统是共享事实源。

### 16.3 回滚验证

- 公共域名重新命中旧机。
- 旧机 5 个服务健康，且新机 worker 明确为 inactive/disabled。
- 真实生图、合同查询、OCR 和自动出餐扫描各通过一次。
- 记录失败原因，在修复并重新完成 No-Go 门禁前不得二次切换。

## 17. 切换后的观察与收尾

### 首小时

- 每 5 分钟检查 5 个 systemd 服务、Caddy 5xx、MongoDB/Supabase/OSS/API 错误。
- 检查自动出餐是否只在新机产生一次扫描记录。
- 检查网关队列、线路暂停状态和 APIMart 待处理任务。
- 保持旧机转发桥，直到超过 DNS TTL。

### 24 小时、72 小时和 7 天

- 比较请求量、错误率、任务数、图片归档数和 OCR 成功率。
- 检查磁盘增长、journal、Caddy 日志轮转、内存和 swap。
- 验证 Caddy 自动 HTTPS 管理没有错误。
- 处理因出口 IP 变化失效的 Cookie/Playwright storage state。
- 第 7 天业务负责人签字后，才从外部白名单删除旧 IP。

### 最终收尾

1. 删除旧机 `authorized_keys` 中带 `cloud-migration-${MIGRATION_ID}` 的临时公钥。
2. 删除新机 `/root/.ssh/id_ed25519_cloud_migration_${MIGRATION_ID}` 及其 `.pub`。
3. 轮换迁移期间暴露面扩大的运维凭证；不要在业务未稳定时同时轮换全部 API Key。
4. 更新所有项目的服务器 IP、SSH 目标、运维文档和监控配置。
5. 旧机释放前再做最终快照（云厂商支持时）或更新本地全量归档，至少保留一种恢复源 30 天。
6. `/srv/legacy-server` 按公司数据保留策略处理；本次 D 盘备份不加密，新机归档必须保持 root-only。
