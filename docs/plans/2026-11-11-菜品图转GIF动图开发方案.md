# 菜品图转 GIF 动图开发方案

日期：2026-11-11。代码基线：`main` / `3284229`。
状态：原始探索方案。2026-11-12起执行用户确认的六种本地动效与平台合规导出，见
`2026-11-12-菜品动图平台导出实施.md`；其规则优先。下文上游任务、数据库和云端归档内容作为后续阶段设计。

后续会话已实际调用线路7并生成文生GIF及图生GIF样例；曾出现静态结果、尺寸/时长偏离、拼图与文字变化。
用户最终选择“纯热气＋上一版五种动态贴纸”，并要求下载满足平台4:3/16:9、2–5秒、GIF/WebP、不超过5M。
因此首期改用原图上可控渲染，不能将下文32MiB、低分辨率试验值或仅模型输出方式作为当前交付规则。

## 1. 目标与结论

用户将已经生成并归档的菜品图片交给 image-2.6，生成保持菜品外观的 GIF 动图。
新增左侧“动图”工作区，以及历史记录中的“动图”分类；原菜品静态图继续保留。

功能可开展，但不能把所有名称含 2.6 的线路直接加入动图调度：

- OpenAI 官方文档支持 GPT Image 2.6 的 GIF 输出和参考图输入。[S1]
- 线路7公开文档支持图生 GIF，并提供异步提交与查询协议；作为首选验证线路。[S2]
- 线路4/6所用漫小白当前公开文档明确限制 GIF 为文生图，不支持参考图和 edits；不满足本需求。[S3]
- 线路2/3所用 Zikl 的本次检索结果不足以确认图生 GIF 能力；保持禁用，等待供应商说明和实测。[S4]
- 当前应用会把归档结果压成 JPEG；只改模型参数或增加按钮，最终仍可能得到静态图。

第一期采用“模型直接生成多帧 GIF → 网关验证 → OSS 保存 GIF → 客户端播放和原样下载”。
不采用视频生成后转 GIF、单张图复制成多帧、逐帧独立生图后拼接等替代方式。
现有视频店招和 FFmpeg 可以后续支持导出变体，但不是本功能上线依赖。

## 2. 能力证据与线路选择

下表区分公开协议、当前代码和账号实际可用性；读取公开文档不等于验证了当前 Key。

| 对象 | 当前模型或协议 | 本次确认的情况 | 第一期处理 |
|---|---|---|---|
| OpenAI 官方 | GPT Image 2.6 Sunburst / Flare | Images API 支持 GIF；参考图路径为 edits | 作为协议参考，不新增直连官方线路 |
| 线路7 / NovaEworld | `gpt-image-2.6` | 文档包含参考图生成 GIF、异步任务 | 首选候选；P0 实测通过后启用 |
| 线路2、3 / Zikl | `gpt-image-2.6` | 当前仓库仅验证静态生图；图生 GIF 未确认 | 不参与 GIF 自动回退 |
| 线路4、6 / 漫小白 | `gpt-image-2.6-flare` | 文档称 GIF 仅文生图，且有 Key 分组限制 | 不参与菜品图转 GIF |
| 线路5 / APIMart | `gpt-image-2` | 当前模型和适配器不属于 2.6 GIF 协议 | 不参与 GIF 自动回退 |

官方和线路7使用 `output_format=gif`、`frame_count`、`frame_duration_ms`。
官方文档的帧数范围为2–16；线路7文档为2–64，不能把供应商扩展视为官方保证。[S1][S2]
线路7参考图异步接口采用 multipart，路径为 `/v1/images/edits/async`。
现有静态编辑适配器的 multipart 构造可复用，但异步任务需要独立适配，保留静态路径。

P0 必须使用当前线路7账号验证：权限、实际多帧输出、参考图保真、任务状态字段、轮询频率、
有效期、失败计费和请求幂等支持。文档没有证明的项目都不得写成已支持。
如果线路7验证失败，第一期停在能力验证阶段；不把参考图丢弃后偷偷改成文生 GIF。

## 4. 产品流程与第一期范围

### 4.1 分类与入口

统一使用：工作区 key `productGif`、业务分类 `product_gif`、显示名称“动图”、MIME `image/gif`。
不要同时引入 `gif`、`animation` 等互相转换的业务分类值。

第一期提供三个入口：

1. “制作1张设计图”的成功结果 → “制作动图”。
2. “制作全店图”的每一张成功结果 → “制作动图”；不自动批量转换20张。
3. “动图”工作区 → 从当前账号已归档的产品图中选择一张。

套餐图若实际归档为 `product`，可沿用相同入口；不将所有其他图片分类默认开放。
来源必须有可查询的归档记录和可访问的可信 OSS 原图。尚未归档成功时禁用入口并说明原因。
动图成功后创建新记录，不替换、重命名或删除原静态图。

### 4.2 工作区

- 左侧展示来源菜品图、店铺和菜品名；选择蒸汽、油光、酱汁流动等轻微动态，以及补充描述。
- 默认要求固定镜头、固定构图，不改变食材、份量、餐具、背景、文字和商标。
- 右侧依次展示排队、生成、归档、完成或失败；关闭页面后可以恢复同一任务。
- 完成卡片提供播放/暂停预览、下载 GIF、查看原图、再次生成。
- 第一期每个账号最多1个进行中的 GIF 任务，不新增10份常驻 GIF 大图缓存。
- “再次生成”是一次新的用户主动生成；“刷新状态/重试下载”不能创建上游生成请求。

### 4.3 历史与预览

历史新增“动图”筛选项；分类条件在服务端分页查询中执行，不能仅过滤当前页。
图片广场和后台历史同样识别动图，并显示尺寸、帧数、总时长、文件体积和实际线路。
列表默认加载 JPEG 首帧封面，用户点击后再挂载 GIF；离屏时卸载动画资源。
暂停通过恢复封面实现，不承诺 `<img>` 能精确暂停在当前帧。
内存中保留任务 ID、元数据和 URL，不持久保存完整 Base64；遵守减少动态效果偏好。
现有复制图片逻辑可能转成 PNG，第一期动图卡片不复用该操作。

## 5. 首期参数与提示词

以下是项目建议值，不是对供应商上限或平台上传规范的声明；P0 验证后固化。

| 参数 | 建议值 / 限制 |
|---|---|
| 输入 | 单张已归档的菜品静态图 |
| 模型 | 线路7的 `gpt-image-2.6`，不由前端任意指定 |
| 帧数 | 默认16，首期允许8/12/16；更高帧数作为供应商扩展另行验证 |
| 每帧时长 | 默认160毫秒；首期允许100/160/200毫秒 |
| 默认时长 | 16 × 160 = 2560毫秒；展示最终文件的实际总时长 |
| 尺寸 | 优先保留原图比例；首批验证512×512、512×384、768×432，不静默裁掉菜品 |
| 请求限制 | 宽高为16的倍数；总帧像素不超过16,777,216；其他上游约束由适配器补充 |
| 文件限制 | GIF 原件最多32 MiB；任务 JSON 响应单独限流限体积；后续若接 Base64 协议需另设编码体积上限 |
| 并发 | GIF 全局先设2、每账号1，同时受既有全局和线路并发约束 |

提示词模板建议保存于 `prompt-templates/`，键名 `product_gif`，由网关渲染：

> 将参考图制作成自然循环的菜品动图。保持原图中菜品、份量、摆盘、餐具、背景与文字不变，
> 镜头固定，仅表现指定的细微动态。动作自然、连续，末尾与开头平滑衔接；不增加手、人、
> 食材或装饰，不让菜品变形，不改变品牌文字。

蒸汽、油光等效果由用户选择，不能根据菜品名称自动给冷饮或凉菜添加不合理蒸汽。
帧数和时长必须传接口参数，不能只写进提示词。循环效果和首尾衔接必须通过实测验收。
GIF 可生成不代表美团或淘宝闪购的每个上传入口都接受 GIF；平台使用规范单独确认，
第一期先提供通用 GIF 下载，不对外宣称“直接适配所有外卖平台”。

## 6. 网关接口与来源校验

以下为拟新增的本项目接口，沿用 `/api` 前缀，与供应商接口区分。

| 接口 | 用途 |
|---|---|
| `GET /api/gif/capabilities` | 返回当前账号是否开放、候选线路和可选参数 |
| `POST /api/gif/jobs` | 创建持久任务，返回202；不等完整 GIF 生成 |
| `GET /api/gif/jobs/:id` | 查询本人任务状态及已归档结果 |
| `GET /api/gif/jobs?active=true` | 恢复当前账号尚未完成的任务 |

创建请求示意：

```json
{
  "source_log_id": "源历史记录UUID",
  "idempotency_key": "本次操作UUID",
  "effect": "steam",
  "motion_prompt": "蒸汽缓慢上升",
  "size": "512x512",
  "frame_count": 16,
  "frame_duration_ms": 160
}
```

`user_id` 从登录令牌得到；店铺、菜品名、平台、源对象 key 由网关查来源记录，
不接受前端伪造的用户、模型、计费或归档成功字段。源记录必须属于当前账号且为 `product`。
不接受任意 `source_url`；限定可信 OSS bucket/域名、允许的对象前缀，并验证文件内容。
复用安全下载器的 DNS、重定向、私网地址、超时和体积限制；不因 GIF 而放宽 SSRF 边界。

第一期沿用现有生成图片引用权限：允许本人历史记录指向已公开给登录用户的生成图片，
只读取经确认的公开生成对象范围，不读取任意 OSS key 或私有对象。这样可以转换既有菜品图，
无需为了补来源标识再次生成静态图。P0 应核对当前 bucket/前缀的实际访问策略。
如果源图片实际为私有对象，则必须先补服务端来源记录或签发凭据，不能只凭可伪造的历史
字段授权读取。`generation_archive_receipts` 也不是强所有权证明，它由历史插入触发器建立。

`GenerationItem` 目前没有历史 ID。新归档响应补充 `history_log_id`，从历史入口直接使用记录 ID；
旧的当前结果可由网关按登录用户、分类和规范化 OSS 对象 key 精确查回归档记录。
查不到记录时引导用户确认归档状态，不能把本地随机 ID 当成数据库 ID。

对外状态响应只包含本项目任务 ID、阶段、必要的结果 URL 和媒体元数据；不返回上游 Key、
原始错误响应、上游任务凭证或内部带签名的临时 URL。日志同样只保留脱敏错误和长度等信息。

## 7. 首选上游适配与验证

线路7公开协议使用 `POST /v1/images/edits/async` 的 multipart 请求；单张来源文件放在
`image` 字段，同时发送 `model=gpt-image-2.6`、`prompt`、`n=1`、`output_format=gif`、
`frame_count`、`frame_duration_ms`、`size`、`response_format=url`。
异步由路径选择，不传未经文档定义的 `async=true`；时长字段无需改名，单位为毫秒。[S2]

受理返回202和 `id` / `task_id`；查询为 `GET /v1/images/tasks/{task_id}`，文档建议间隔2秒。
状态为 `queued`、`in_progress`、`completed`、`failed`，成功文件位于 `result.data[0].url`。
任务失败也可能返回 HTTP 200，因此必须判断业务状态。P0 用真实脱敏响应核对并建立契约测试。

源图先经过内容和下载边界验证，再以文件上传；multipart boundary 由 HTTP 客户端生成。
异步接口仅接受 URL 结果模式，完整上传请求体上限32 MiB；不套用同步接口的 Base64 返回选项。
查询必须使用原提交 Key，任务表只存凭据版本引用，不存真实 Key；轮换时保留在途任务的查询能力。
这些是供应商公开协议，当前账号可用性、结果保留期和实际输出质量仍需 P0 验证。[S2]

P0 的最小真实试验：先做一次低帧数小尺寸参考图生成，成功后再验证默认16帧设置。
逐项记录但不公开敏感响应：

1. 当前 Key 是否允许图生 GIF，是否需要特殊分组或单独开通。
2. 提交是否返回可恢复任务 ID，查询是否要求相同 Key，任务查询和文件保留多久。
3. 返回是否确实是 GIF、多于1帧、存在实际画面变化，而非 PNG 或仅扩展名为 GIF。
4. 请求帧数/时长与实际文件是否一致，是否被供应商调整。
5. 主体、餐具和文字是否保持，是否自然循环。
6. 耗时、体积、实际计费；失败、超时及重复请求是否收费。
7. 供应商是否支持请求幂等或按请求标识查询，不能凭经验假定支持。

只在全部关键项通过后将线路7标记为 `reference_gif` 可用。线路2/3后续也必须逐项验证，
不能因为静态图片健康检测通过就加入 GIF 调度。线路4/6文生 GIF 能力留待另一个需求处理。

## 8. 持久任务、并发与重试

新增 `gif_generation_jobs`，由网关持久保存；不能把重启恢复依赖于浏览器内存或仅 Tokio spawn。
第一期复用现有 Supabase/Postgres，不为这一功能引入 Redis 或另一套外部队列。

建议状态：

```text
queued → submitting → running → downloading → archiving → succeeded
                     ↘ failed
submitting / running → reconciling（上游状态不确定，禁止自动重新提交）
```

- `(user_id, idempotency_key)` 唯一；相同键和参数返回原任务，不同参数返回409。
- 提交前持久保存任务和已选线路；拿到上游 ID 后立即持久保存，再开始轮询。
- 上游已接单但响应丢失、或保存任务 ID 失败时，进入待核对状态；不换线路重新生成。
- 客户端轮询可指数退避并加抖动；关闭页面或断网只停止客户端轮询，不撤销上游任务。
- 超时是等待预算耗尽，不等于供应商明确失败；已接单的任务保留可恢复状态。
- worker 通过数据库原子 claim/租约领取任务；续租、进程重启和过期租约恢复都要有测试。
- 数据库事务不得跨越上游 HTTP 请求；多 worker 领取同一任务时只有一个可执行提交。
- 已提交任务直到供应商完成前占用逻辑生成容量；不能收到202就立即释放线路额度。
- 网关重启后先恢复在途占用和待核对任务，再接纳新任务，避免恢复瞬间超卖并发。
- 下载和 OSS/数据库归档失败只重试对应阶段；不重新调用生成接口。
- 只有能证明供应商未受理的失败才允许有限重试，并遵守已验证的线路能力集合。

复用既有队列限流、账号鉴权、OSS 归档并发和错误分类原则；GIF 增加自己的配额。
第一期不承诺真正的上游取消；界面不能把“停止查看”标成“取消成功”或“不会计费”。
任务启动、后台进行和归档阶段要进入应用忙碌统计，避免用户被更新流程中断；
重启后通过服务端任务列表恢复，不要求保留现有工作区全部内存。

## 9. GIF 验证、归档与下载

### 9.1 结果验证

不能仅依赖响应 `Content-Type` 或 URL 后缀。下载/解码均限制字节数、尺寸、帧数、
累计解码像素、总时长和处理时间；防止小文件声明超大画布导致内存耗尽。
在受控解码器中验证 GIF87a/GIF89a 签名、完整帧结构、至少2帧、合理帧时长和实际动态。
画面差异应比较正确合成后的帧，考虑局部帧和 disposal，不能只比较压缩片段。
逐帧处理，避免同时驻留所有完整 RGBA 帧；尺寸、时长以解码所得元数据为准。
循环扩展和首尾衔接单独验收；不能只靠提示词宣称一定无限循环。
供应商明确提示目标格式、帧数和时长不保证严格遵循。[S2] 静态结果在本项目标记为
`invalid_animation`，不归档为成功动图、不自动重新生成；有效多帧结果若仍在资源预算内，
允许帧数或时长与请求不同，展示实际值。再次生成需用户主动发起，并说明会产生新一次请求。

### 9.2 保存

- 原 GIF 不经过 `compress_generated_image`、JPEG 编码器或静态缩放函数。
- OSS `Content-Type` 为 `image/gif`，文件扩展名为 `.gif`；MIME 必须与真实内容一致。
- 原件使用确定性 key，例如 `generated-gif/<user_id>/<job_id>/result.gif`。
- 另存首帧预览 `preview.jpg`，仅该预览可以走静态压缩，不另算一次生成。
- 归档记录保存原件 SHA-256、大小、尺寸、帧数和总时长；不长期依赖供应商临时下载 URL。
- OSS 成功后才执行数据库归档完成事务；确定性 key、任务 ID 和唯一约束共同防止重复归档。
- OSS 与 Postgres 不是一个事务：崩溃恢复需先检查既有对象与摘要，再补写记录；
  不把“上传完成”直接标为“全部成功”。临时文件清理和孤立对象清理由独立补偿处理。

当前 `oss.rs` 会重新生成带时间的 key，需要为 GIF 增加受控的确定性对象写入入口；
不能只把 job ID 放在文件名里却仍每次生成不同时间前缀。该入口不得向客户端开放任意 key 写权限。

### 9.3 下载

动图下载采用原始二进制复制，文件名例如 `店铺名_菜品名_动图.gif`。
保存对话框仅提供 GIF 类型，原字节下载与归档摘要一致；禁止掉入现有 `.jpg/.png` 缩放兜底。
需要缩放、减帧或转 MP4 时另建显式导出功能，保留原 GIF，不在首次版本悄悄做有损变换。

## 10. 数据库、分类与统计

### 10.1 持久任务

`gif_generation_jobs` 至少包含：

| 分组 | 字段建议 |
|---|---|
| 标识 | `id`、`user_id`、`idempotency_key`、请求参数摘要 |
| 来源 | `source_log_id`、源对象 key/摘要、店铺/菜品/平台快照、来源范围校验结果 |
| 请求 | `effect`、用户动态描述、prompt 模板版本与渲染后快照、尺寸、帧数、帧时长 |
| 调度 | 实际线路/模型、凭据版本引用、上游任务 ID、状态、租约拥有者/到期时间、下一次轮询时间 |
| 结果 | 固定 OSS key、预览 key、媒体元数据、归档日志 ID、结果摘要 |
| 诊断 | 创建/开始/完成时间、各阶段尝试次数、脱敏错误码 |

此表只允许服务端角色读写，启用 RLS 并撤销普通用户的直接写权限；客户端经网关查询本人任务。
不要将明文 Key 或签名 URL 长期存入任务行。源历史引用可为空且不级联删除任务；
记录创建时保留必要快照，避免7天历史清理破坏在途任务。

### 10.2 归档历史

在完整 schema 和新增迁移中同步放行 `asset_kind='product_gif'`。
为 `generation_logs` 增加可空媒体字段：`mime_type`、`width`、`height`、`frame_count`、
`duration_ms`、`file_size_bytes`、`preview_oss_url`、`preview_oss_key`、`generation_job_id`。
可变帧时长以总时长为准，不强行假定每帧时间相等；旧静态记录保持可空并按旧逻辑解释。
`generation_job_id` 建唯一索引，动图元数据增加合理 CHECK，不追溯要求旧记录填满。

完成归档使用服务端事务/RPC：插入或查回唯一历史记录 → 触发现有成功计数 → 更新任务为成功。
原有 `generation_archive_receipts` 去重和新任务唯一性都要保留；重复完成、并发恢复和事务回滚
不能多计数。若历史已被清理，重放旧完成事件仍不能借机创建新的历史和再次计数。
主分支幂等迁移 `20261111_generation_archive_idempotency.sql` 的生产部署状态需要先核对，
不能把“源码已推送”视为“数据库已具备去重能力”。

建议一个成功 GIF 计为1次成功作品；不按帧计数，源静态图原来的计数不变。
实际供应商消耗单独记录，不能用成功作品数当作准确账单。
日统计视图追加 `product_gif_count`，后台、网关统计和 TS 类型同步；保留现有列次序和含义。
新 GIF 分类应限制为服务端归档写入，不能让普通客户端直接插入一个动图 URL 伪造完成。

### 10.3 保留周期

GIF 历史沿用当前7天可见策略；任务详情、失败诊断和临时文件另设清理策略。
去重凭据保留最小标识，不能随7天历史一起删除后允许旧任务重新计数。
7天历史记录清理不等同于 OSS 自动删除；上线前确认并配置原件、封面和孤立对象的生命周期。
如果按时间删除 OSS 对象，需确保不会删除在途任务仍依赖的源文件。

## 11. 旧客户端兼容与上线顺序

旧客户端不会自动理解 `product_gif`：历史标题、下载分类和静态缩放兜底都有风险。
它们直接查询 `generation_logs`，所以只隐藏新按钮或关闭新客户端入口不能隔离旧客户端。

第一期采取“所有受支持员工电脑先升级兼容客户端，再启用 GIF”的发布策略：

1. 确认线路7能力与来源验证方案，功能开关默认关闭。
2. 执行可重复的数据库增量迁移；部署带 GIF 路由、worker 和恢复逻辑的网关。
3. 发布能识别 GIF 分类、展示封面、原样下载和恢复任务的新客户端。
4. 在 Windows 验证安装、覆盖更新和 GIF 全流程，确认员工电脑已完成兼容升级。
5. 仅对灰度账号开放线路7，观察成功率、耗时、文件体积、内存、费用和重复归档。
6. 验收通过后扩大范围，保留快速关闭新任务入口的开关。

当前更新提示允许“稍后更新”。设置 `update_enabled` 或 `force_update` 不等于所有电脑已升级。
若业务不能保证旧客户端完成升级，不得直接启用向共享历史写入新分类；应先另行设计旧客户端
历史隔离（如独立 GIF 历史存储与新接口），不能在上线时临时把 GIF 冒充 `product`。

回滚时关闭新建任务，保留已提交任务的轮询、下载和归档恢复；保留新列和已成功 GIF。
已经写入 GIF 历史后，不可把客户端降回不识别 GIF 的旧版；仅回滚入口或模型路由。
数据库迁移、网关部署与 Windows 安装包是三项独立发布，源码推送不会替代它们。
