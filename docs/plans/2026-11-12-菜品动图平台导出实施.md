# 菜品动图：平台规范与本地制作实施

日期：2026-11-12。需求来源：用户提供的平台上传要求，以及本次会话确认的六种风格。
本文件优先于《2026-11-11-菜品图转GIF动图开发方案》中相冲突的首期实现、格式、参数和导出规则。

## 1. 平台规则（下载硬约束）

| 项目 | 平台要求 | 本项目执行 |
|---|---|---|
| 时长 | 建议2–5秒，不超过5秒 | 仅提供2、3、4、5秒，默认3秒；验证文件实际帧时长之和 |
| 比例 | 4:3、16:9 | 使用整数交叉相乘校验精确比例，不用四舍五入或宽松误差 |
| 4:3分辨率 | 大于750×562 | 宽>750且高>562；默认1024×768 |
| 16:9分辨率 | 大于750×422 | 宽>750且高>422；默认1024×576 |
| 格式 | 仅GIF、WebP | 验证真实编码、至少2帧及实际画面变化，不仅检查后缀 |
| 大小 | 不超过5M | 按更严格的5,000,000字节执行；拒绝超限文件 |

这是用户提供的上传规范，未宣称适用于所有平台入口。格式、比例、时长、尺寸和体积全部通过后
才能出现可交付结果；下载时再次读取文件并验证。失败不能把文件改扩展名或压成静态图交付。

## 2. 原图尺寸与平台画布

之前约定“输出尺寸等于原图”，现在以用户最新的平台上传要求为准：

1. 原图已经是所选精确比例、达到平台下限，且不超过2048×1536时，保持原图尺寸。
2. 不符合比例或尺寸条件时，明确展示原图尺寸与输出尺寸，完整等比适配到所选平台画布。
3. 不拉伸、不裁切、不自动删除文字，空白区域补深色背景。
4. 1024×771不是精确4:3。平台4:3输出为1024×768，预览展示完整适配效果。
5. 编码后超5M仅尝试降低颜色数、WebP质量和帧率，不在后台偷偷缩小选定画布。
6. 仍不合规时显示失败，建议用户主动选择WebP或更短时长；不产生不合规的可下载结果。

## 3. 用户确认的六种风格

采用上一版“大幅动态贴纸＋热气”的视觉，不采用后来被否定的国潮书法版。

| 标识 | 名称 | 动画 |
|---|---|---|
| `steam` | 热气腾腾 | 以用户确认的牛肉板面GIF为参考：自然热气、菜品/汤面细微动态，无新增贴纸或图标 |
| `aroma` | 真香 | 真香贴纸上下跳动、热气升腾 |
| `sparkle` | 美味 | 美味贴纸摇摆、金色星芒闪烁、热气 |
| `flame` | 好吃 | 好吃文字弹跳、火焰伸缩、热气 |
| `heart` | 爱了 | 贴纸心跳缩放、爱心上浮、热气 |
| `recommend` | 必点 | 推荐章摇摆、箭头指向菜品、热气 |

所有效果均保持背景菜品和原有标题稳定，按固定时间轴绘制，默认20fps。
当前`steam`实现只是可控蒸汽叠加，未达到用户确认的自然动效参考，不能因导出校验通过就宣称视觉验收通过。
界面已提示这一差距，不冒充重新调用image-2.6的结果。贴纸使用系统中文字体，Windows与macOS
具体字形可能略有差异；动画位置按画布相对坐标计算。

### 3.1 第一种风格的唯一验收参考（2026-11-12补充确认）

用户再次上传并明确指定`output/imagegen/牛肉板面加卤蛋-美食动图.gif`为第一种风格。
该文件是此前线路7图生GIF的结果，435×384、9帧、1620毫秒；只作为视觉参考，原文件不满足当前平台导出规范。

- 名称为“热气腾腾”，沿用已有`steam`标识，避免破坏已保存的本机结果。
- 自然白色热气从碗和菜品处升腾、扩散、消散；菜品/汤面有轻微自然动态。
- 镜头、餐具、摆盘和原有招牌保持稳定，不添加“真香”等文字、贴纸、星星、火焰、箭头或爱心。
- 参考的是动效观感，不沿用参考文件的低分辨率、短时长或模型造成的构图变化。
- 简单曲线热气叠加只能作为当前本地预览，不能作为这一风格已完成的依据。
- 用户明确只接受原参考效果：后续实现必须恢复原方案的模型图生动图接入，不使用本地蒸汽、噪声纹理或热浪模拟替代。视觉和平台合规两项分别验收。
- 第一种风格的自然动效仍待实现与验收。本次修订只固定参考、名称和状态说明，其余五种已确认风格保持不变。

## 4. 当前实现范围

本次完成桌面端本地制作闭环：

- 左侧新增“动图”工作区，选择静态菜品图片、风格、比例、时长和GIF/WebP。
- 单张产品结果、全店图的单张结果、产品历史记录增加“制作动图”入口。
- Canvas实时预览，暂停/播放；切换工作区不丢失任务状态。
- Canvas逐帧绘制PNG，经Tauri IPC逐帧传送到受控缓存，不在内存积压所有PNG/Base64。
- Rust调用安装包已有FFmpeg编码，最终用Rust图像解码器逐帧验证真实格式、尺寸、时长、画面变化和体积。
- 结果保存在应用本地数据目录，按账号UUID隔离，提供最近50条本机动图分类记录和再次下载。
- 制作期间纳入全局忙碌状态，阻止刷新/自动更新中断；取消清理临时帧并终止正在执行的编码进程。
- 不调用收费上游，不要求新增服务器服务、数据库迁移或读取本地私密配置。

本次未启用：云端OSS动图归档、跨电脑共享动图历史、图片广场动图、持久上游异步任务。
本机记录不等同于云端历史，不把GIF伪装成`product`上传已有JPEG归档链路。
应用关闭后保留成功作品，未完成的本地帧任务不承诺自动恢复；下次启动制作时清理过期缓存。

## 5. 文件与接口

| 文件 | 作用 |
|---|---|
| `src/lib/product-animation/policy.ts` | 六种风格、平台尺寸选择、前端交付校验 |
| `src/lib/product-animation/render.ts` | 基于原图的可控热气/贴纸Canvas渲染 |
| `src/lib/product-animation/source.ts` | 产品结果、历史到动图工作区的来源传递 |
| `src/lib/product-animation/desktop.ts` | 本机记录、预览URL、保存对话框和下载 |
| `src/hooks/useProductAnimation.ts` | 常驻状态、逐帧制作、取消、结果列表 |
| `src/components/workspace/ProductAnimationWorkspacePage.tsx` | 动图工作区 |
| `src-tauri/src/product_animation.rs` | 参数与最终GIF/WebP内容检查 |
| `src-tauri/src/product_animation/commands.rs` | 缓存会话、编码、取消、本机记录、下载 |

Tauri命令：`begin_product_animation` → `append_product_animation_frame` → `finish_product_animation`。
辅助命令：`cancel_product_animation`、`list_product_animations`、`save_product_animation`。
会话ID由Rust生成，帧序号必须连续，数量不能超过时长要求；只允许PNG帧，尺寸必须与会话一致。
编码最多三次：GIF颜色256/128/64；WebP质量82/65/45；帧率20/15/10。
每次编码有120秒超时和取消检查；一次只允许一个本地编码任务。

## 6. 验收与后续顺序

已完成验证：

- 前端完整测试131/131通过；`npm run build`通过，保留原有大包与混合导入提示。
- Chromium实际挂载工作区，测试上传、六种风格、比例/格式/时长选择、暂停与浏览器环境提示。
- 从产品Canvas渲染器实际导出六组各60帧，再经Rust生产编码与解码路径生成12份GIF/WebP。
- 12份文件全部为1024×768、3000毫秒、60帧；体积650,102–2,224,723字节，首次编码均通过。
- 浏览器逐帧检查原标题固定，每个风格的菜品热气区域均有60个不同画面。
- Rust测试覆盖精确比例、下限、时长、格式、超体积、损坏文件、实际GIF/WebP和编码取消。
- Rust全库回归129通过、2忽略；补充时长修正回归后，动图专项5/5通过。真实六风格帧导出测试已单独执行通过。
- WebP编码器可能产生1999毫秒的舍入结果；实现按实际ANMF帧数修正帧时长，使总时长精确等于选择值，再解码验证。
- 当前macOS的Homebrew精简FFmpeg缺少WebP编码；本机安装`ffmpeg-full`完成验证。Windows打包媒体工具声明包含libwebp，仍需Windows实机验收。

本机样例与截图位于`output/imagegen/平台合规动图/`（生成物目录，不提交到源码库）。
