## Synthesized Findings

### 当前问题

```text
上游生成原图
  -> 网关持有完整 Base64
  -> 网关压缩并上传 OSS
  -> 网关又把完整 Base64 放入 JSON 返回客户端
```

Base64 比原始二进制约多 33% 体积。高并发时，网关到客户端的重复大响应会持续占用服务器公网出口，是被平台智能限速的主要可消除流量。

### 目标数据流

```text
上游生成原图
  -> 网关压缩为可交付规格并上传 OSS
  -> 网关只返回短 JSON 和签名 URL
  -> 客户端直接从 OSS 下载
  -> 客户端本地转换为 Base64
  -> 现有预览、复制、缩放和导出流程保持不变
```

### 兼容结论

- 不能直接删除 `image`，否则已安装的旧客户端会立即失效。
- 请求增加可选 `result_delivery`，默认值必须是 `inline_base64`。
- 新客户端显式请求 `oss_url`；成功时 `image = null`，并返回 `image_url`。
- URL 模式归档失败时自动降级为 `inline_base64`，同时返回 `archive_error`。
- 新客户端必须同时支持“新网关 URL 响应”和“旧网关内联响应”，这样服务器和客户端都可独立回滚。
- URL 模式必须携带 `archive` 参数；缺失时在调用上游前返回 400，避免生成完成后没有交付对象。

### 非目标

- 本次不把上游生图调用移出网关，API Key 仍只保存在服务器。
- 本次不改变 Supabase Auth、历史记录和 OSS 对象命名边界。
- 本次不能消除“上游到网关”和“网关到 OSS”的流量，只消除网关向新版客户端重复发送图片的流量。

### 已实现契约

- Rust 请求增加 `ResultDelivery`，默认 `inline_base64`。
- URL 模式缺少 `archive` 时在上游调用前返回 400。
- URL 模式归档成功时 `image = null`，返回 `image_url`；归档失败自动回退内联 Base64。
- 新客户端 `generateArchivedImageWithLine` 显式请求 `oss_url`，同时兼容旧网关的字符串/内联响应。

- 各工作区仍使用 `rawBase64`，新增正确 MIME 的 `imageDataUrl` 传播，避免把 OSS JPEG 错标为 PNG。
