# 自动更新

本文档记录“呈尚策划美工生图系统 PRO”桌面端强制自动更新的当前实现、运行流程，以及以后每次发布新功能后的更新操作步骤。

## 一、当前更新架构

自动更新由两部分组成：

| 位置 | 作用 |
|---|---|
| Supabase 云数据库 | 存储最新版本号、是否强制更新、安装包下载地址、更新内容 |
| 阿里云 OSS | 存储实际的 `.exe` / `.msi` 安装包文件 |

当前不是把安装包放在云服务器网关上。云服务器不承担安装包下载流量。

实际流程是：

```text
软件启动
  ↓
读取 Supabase public.app_update_config
  ↓
判断 latest_version 是否高于本机版本，且 force_update=true，且 installer_url 不为空
  ↓
需要更新时弹出强制更新窗口
  ↓
用户点击“自动更新”
  ↓
Tauri/Rust 流式下载 OSS 安装包到本机缓存目录，并向弹窗上报进度
  ↓
进度条到 100%
  ↓
启动安装程序
  ↓
退出旧软件
  ↓
安装完成后自动重新打开新版本
```

## 二、Supabase 配置表

表名：`public.app_update_config`

关键字段：

| 字段 | 说明 |
|---|---|
| `id` | 固定为 `desktop` |
| `latest_version` | 云端最新桌面版本号，例如 `3.0.1` |
| `force_update` | 是否强制低版本客户端更新 |
| `installer_url` | 阿里云 OSS 安装包签名下载链接 |
| `release_notes` | 更新内容，每行一条 |
| `updated_at` | 更新时间 |

当前云端配置为（2026-09-07 发布）：

```text
latest_version = 3.0.30
force_update = true
installer_url = 已写入 app-updates/3.0.30/ 下的 OSS 签名下载链接
release_notes = 制作1张设计图新增产品名称显示方式，可选择带产品名称或不带产品名称。
选择不带产品名称时，生成提示词不再写入产品名，并同步放宽产品名称必填校验。
保持制作全店图的产品名称显示方式不变，单张与全店图交互一致。
```

`3.0.30` NSIS 安装包（53,258,260 字节）SHA-256：

```text
c28ddc08bbf94fd001901b886847bf415464a2877cb3bd9f36761f4dfc45a428
```

`3.0.30` MSI 安装包（66,523,136 字节）SHA-256（备用人工安装包）：

```text
ae31834692147a34f78d714e029cf7b0c9b3dac081eefa839d0854196bb48738
```

发布前已使用项目生产环境构建 `3.0.30`，并完成 NSIS/MSI 产物、OSS 上传、公开 Range/CORS 验收。两个安装包上传均返回 HTTP `200`，公开 Range 下载均返回 HTTP `206`、CORS 为 `*`；确认灰度配置正确后才将 `force_update` 改为 `true`。

公开接口最终确认版本为 `3.0.30`、安装包地址非空且强制更新已开启。

本次更新了桌面客户端安装包、制作1张设计图的产品名称显示方式与 Supabase 强制更新配置，未调整 Caddy。

本次通过本机生产 `.env.local` 注入 OSS 上传环境，并通过云服务器生产私密环境写入 Supabase 配置；未在文档中记录任何密钥或完整签名 URL。

## 三、客户端判断逻辑

软件启动后会执行以下判断：

1. 读取本机版本号，版本来自 `package.json`，构建时由 Vite 注入到前端。
2. 请求 Supabase `app_update_config` 表中的 `desktop` 配置。
3. 如果以下条件同时满足，则弹出强制更新窗口：
   - `force_update = true`
   - `latest_version` 高于当前本机版本
   - `installer_url` 不为空
4. 如果本机版本已经等于或高于 `latest_version`，不弹窗。
5. 如果 `force_update = false`，不弹窗。

强制更新窗口会遮住整个软件，用户不能关闭，也不能继续使用旧版本。

## 四、点击“自动更新”后的安装流程

用户点击“自动更新”后：

1. 前端调用 Tauri 命令：`install_app_update`
2. 强制更新弹窗显示下载进度条：
   - 下载开始时显示 0%
   - Rust 每写入一段安装包数据，上报一次下载进度
   - 下载完成后显示 100%，并切换为正在启动安装程序
3. Rust 端校验安装包地址：
   - 只允许 `http://` 或 `https://`
   - 只允许 `.msi` 或 `.exe`
4. Rust 端流式下载安装到本机缓存目录：
   - 应用缓存目录下的 `updates/<latest_version>/`
5. 下载完成后启动安装程序：
   - `.msi`：`msiexec.exe /i <安装包> /passive /norestart`
   - `.exe`：`<安装包> /S`
6. 启动安装程序后，当前旧软件自动退出。
7. 独立后台 helper 等待安装程序结束，然后自动打开软件。

## 五、为什么安装包放 OSS

安装包是大文件，更适合放阿里云 OSS：

- OSS 更适合静态大文件分发。
- 不占用云服务器网关带宽。
- 可以使用签名 URL 控制访问。
- 可以按版本保存，例如 `app-updates/3.0.2/...`。
- 回滚时只需要调整 Supabase 配置指向旧版本安装包。

云服务器更适合做业务接口，不适合直接扛所有员工下载安装包的流量。

## 六、重要限制

自动更新能力只能从“已经内置更新器”的版本开始生效。

也就是说：

- 如果员工电脑上的旧软件完全没有自动更新代码，它不会主动检查 Supabase，也不会弹窗。
- 这类旧软件必须先人工安装一次带更新器的版本，例如 `3.0.1`。
- 从 `3.0.1` 之后，再发布 `3.0.2`、`3.0.3`，就可以走自动更新。

同理，更新弹窗进度条和“安装完成后自动重新打开软件”只能从已经内置该逻辑的版本开始生效。

- 低于 `3.0.4` 的客户端更新到 `3.0.4` 时，下载和安装动作仍由旧客户端执行，因此那一次不一定显示进度条，也不一定能自动重开。
- 从 `3.0.4` 之后，再发布 `3.0.5` 或更高版本时，低于新版本且已经是 `3.0.4+` 的客户端会显示下载进度，并在安装完成后自动重新打开软件。

## 七、下次发布新功能时的标准步骤

下面假设下一个版本为 `3.0.2`。实际发布时把命令和 SQL 中的版本号替换为真实版本号。

### 1. 完成代码改动和本地测试

先完成新功能或修复，然后跑对应测试。

至少保留自动更新相关测试：

```powershell
npx tsx tests/mandatory-update.test.ts
npx tsx tests/sidebar-layout.test.ts
npm run build
```

如果改到 Rust/Tauri 侧，额外跑：

```powershell
cmd.exe /c 'call "D:\Program Files (x86)\Microsoft Visual Studio\2022\BuildTools\Common7\Tools\VsDevCmd.bat" -arch=x64 >NUL && cargo test --manifest-path src-tauri\Cargo.toml app_update'
```

### 2. 升级版本号

需要同步这些位置：

| 文件 | 要改的位置 |
|---|---|
| `package.json` | `"version"` |
| `package-lock.json` | 根版本号和 packages 根版本号 |
| `src-tauri/Cargo.toml` | `version = "..."` |
| `src-tauri/tauri.conf.json` | `"version"` |
| `src/components/Sidebar.tsx` | 侧栏底部显示的 `v...` |
| `tests/sidebar-layout.test.ts` | 版本断言 |

示例：把所有 `3.0.1` 改成 `3.0.2`。

### 3. 构建桌面安装包

运行：

```powershell
npm run tauri:build
```

成功后会生成两个包：

```text
src-tauri/target/release/bundle/msi/呈尚策划美工生图系统PRO_<版本号>_x64_zh-CN.msi
src-tauri/target/release/bundle/nsis/呈尚策划美工生图系统PRO_<版本号>_x64-setup.exe
```

当前自动更新优先使用 NSIS `.exe` 包。

### 4. 上传安装包到 OSS

建议每个版本单独一个目录，不要混放：

```text
app-updates/3.0.2/csgh-image-studio-3.0.2-x64-setup.exe
```

上传后生成一个签名下载 URL，建议有效期足够长，例如 1 年。

仓库提供 `scripts/publish-app-update.mjs` 自动执行上传、Range/CORS 验证、灰度配置和强制更新开关。脚本只从进程环境读取凭据，不会输出密钥或完整签名 URL；推荐依次执行：

```text
upload-msi <MSI路径> <版本号>
stage <NSIS路径> <版本号> <更新说明Base64>
status
enable <版本号>
```

`stage` 会固定写入 `force_update=false`，`enable` 会先核验灰度版本和安装包地址，再开启强制更新。运行环境必须由服务器私密环境文件注入凭据，不要把凭据写入命令、文档或仓库。

注意：

- 不要把真实 OSS AccessKey 写进文档或提交到仓库。
- 不要把真实签名 URL 提交到 Git。
- 如果签名 URL 过期，只需要重新生成 URL 并更新 Supabase 的 `installer_url`。

### 5. 先写云端配置，但暂时不要强制

建议先把 `latest_version` 和 `installer_url` 写上，但 `force_update=false`，避免安装包 URL 写错时直接影响员工。

SQL 模板：

```sql
update public.app_update_config
   set latest_version = '3.0.2',
       force_update = false,
       installer_url = '替换为新的 OSS 签名下载链接',
       release_notes = '新增 xxx 功能
修复 xxx 问题
优化 xxx 体验',
       updated_at = now()
 where id = 'desktop';
```

### 6. 验证云端配置可读

用 Supabase anon 公开读取确认：

```text
id = desktop
latest_version = 3.0.2
force_update = false
installer_url 非空
release_notes 正确
```

同时用浏览器或脚本访问 `installer_url`，确认安装包可以下载。

### 7. 打开强制更新

确认安装包可下载后，再打开强制更新：

```sql
update public.app_update_config
   set force_update = true,
       updated_at = now()
 where id = 'desktop';
```

从此以后：

- 低于 `3.0.2` 的客户端启动后会弹强制更新。
- 已经是 `3.0.2` 或更高版本的客户端不会弹。

### 8. 发布后验证

建议用一台低版本测试机验证：

1. 启动旧版本。
2. 应弹出“检测到新版本”窗口。
3. 更新内容应清晰可读。
4. 点击“自动更新”。
5. 安装包应开始下载，弹窗应显示进度条。
6. 进度到 100% 后应自动启动安装程序。
7. 软件退出。
8. 安装完成后应自动重新打开，侧栏版本号应变为新版本。

## 八、暂停或回滚

### 暂停强制更新

如果发现安装包有问题，立即执行：

```sql
update public.app_update_config
   set force_update = false,
       updated_at = now()
 where id = 'desktop';
```

这样新启动的软件不会再弹强制更新。

### 回滚到旧版本

如果需要回滚，比如从 `3.0.2` 回到 `3.0.1`：

1. 确认 OSS 上仍有 `3.0.1` 安装包。
2. 生成 `3.0.1` 安装包的签名下载 URL。
3. 更新 Supabase：

```sql
update public.app_update_config
   set latest_version = '3.0.1',
       force_update = true,
       installer_url = '替换为 3.0.1 的 OSS 签名下载链接',
       release_notes = '回滚到 3.0.1 稳定版本',
       updated_at = now()
 where id = 'desktop';
```

注意：如果用户本机已经是 `3.0.2`，而 `latest_version` 改成 `3.0.1`，客户端版本比较会认为本机版本更高，不会弹窗降级。真正需要降级时，建议人工安装旧包，或发布一个更高版本号的修复包，例如 `3.0.3`。

## 十、发布前检查清单

每次正式打开 `force_update=true` 前，至少确认：

- [ ] 版本号已全部同步。
- [ ] 构建产物已确认只包含生产 Supabase 项目，不能指向测试项目。
- [ ] `npx tsx tests/mandatory-update.test.ts` 通过。
- [ ] `npx tsx tests/sidebar-layout.test.ts` 通过。
- [ ] `npm run build` 通过。
- [ ] `npm run tauri:build` 成功生成安装包。
- [ ] OSS 安装包可以下载。
- [ ] Supabase `installer_url` 已写入且可公开读取。
- [ ] `force_update` 是最后一步才打开。
